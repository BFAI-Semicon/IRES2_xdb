# OCR 登録の処理方式検討

検討日: 2026-09-03  
対象: OCR で実験データを登録するとき、読み取りをブラウザ内で行うか、サーバーで行うか  
参照: `.kiro/specs/ocr-registration/brief.md`、`docs/requiests.md`、`CONTEXT.md`

## 結論

- 自前運用のサーバーで OCR し、結果を Web アプリ上で確認・訂正してから登録する方式を推奨
- 確認・訂正の画面はどちらの方式でも Web アプリ側に置くため、ユーザーの操作は変わらない
- 撮影した画像は添付として実験データに残し、読み取り結果の根拠とする
- 外部の LLM API は費用と情報の外部送信の面で使えない可能性がある。エンジンは組織内で動くものから選ぶ

## 前提

オフラインなのは装置であり、ユーザーの手元の端末ではない。本システムへの登録自体がサーバー通信を要するため、画像をサーバーへ送ることで制約は増えない。

読み取りの対象は要望メモにある 2 つ。いずれも汎用 OCR エンジンの苦手分野。

- 装置の表示パネル（7 セグメント表示、液晶画面）
- 紙のノートの手書き数値

## 方式の比較

| 観点             | ブラウザ内 OCR                       | サーバー側 OCR                                 |
| ---------------- | ------------------------------------ | ---------------------------------------------- |
| エンジン         | WASM 版（Tesseract.js など）に限る   | 自由。組織内で動くモデルを選べる               |
| 手書き・パネル   | 弱い                                 | 前処理や専用モデルで改善可。読み取り規則も可   |
| 初回の負荷       | モデルの取得に数十 MB                | なし                                           |
| 端末の処理       | タブレットでは遅い                   | 軽い                                           |
| 精度の改善       | 端末ごとに結果が変わり、一括改善不可 | サーバーで一括管理                             |
| 画像の扱い       | 端末から出ない                       | 送信し、添付として正本に残す                   |
| 通信             | 読み取りのみ不要。登録には必要       | 読み取り・登録とも必要                         |

ブラウザ内 OCR の利点は「画像を端末から出さない」ことだけであり、本システムでは画像を添付として残す方針のため、この利点は活きない。サーバーが組織内にあれば、画像は組織の外に出ない。

## エンジンの候補

外部の LLM API（Claude、GPT など）は精度は高いが、1 回ごとの費用と、画像を外部へ送ることの可否が壁になる。使えない前提で、組織内で動く候補を並べる。

| 候補 | 費用 | 得意 | 注意 |
| --- | --- | --- | --- |
| Tesseract、PaddleOCR | 無料、CPU で動く | 印字、液晶の数字 | 7 セグメントは前処理か専用認識器が必要 |
| 7 セグメント専用（ssocr 等） | 無料、CPU で動く | 7 セグメント表示 | 撮影角度と切り出しに敏感 |
| 手書き数字の小型モデル | 学習の手間 | 数値・単位の狭い語彙 | 現場の紙で学習データを集める必要あり |
| 公開重みの画像対応 LLM | GPU 機材の初期費用 | 手書き、レイアウトの混在 | 運用負荷が高い。上の候補で足りるか先に確認 |

読み取る内容は数値と単位が中心で語彙が狭い。従来型 OCR と前処理の組み合わせで先に試し、足りない装置だけ次の候補に進めるのが費用面で無理がない。

## 公開重みの画像対応 LLM の評価

印字や液晶の数字は実用域。7 セグメント表示と手書きは、実物の写真で試すまで断言できない。

- 得意: 印字文書、日本語の印字、液晶画面の数字、表のような並び。商用 API に近い水準
- 不安: 7 セグメント表示（8・0・6・9、小数点、マイナス記号の取り違え。反射や斜め撮影で悪化）、手書き数値（字形の差、指数表記）、単位や桁の取り違え（mTorr と Torr など）
- 固有の危険: 読めなくても「それらしい数値」を自信ありげに返す。従来型 OCR のように空欄や低い確信度で止まらない。文字単位の確信度も信頼しにくい。実験記録では誤った数値が正しい数値より害が大きい
- 機材: 7B から 8B クラスで GPU メモリ 16 GB 程度、量子化で 8 GB。2B から 3B は CPU でも動くが精度が落ちる。30B 以上は機材費が跳ねる
- 対策: 表示部分だけを切り出して渡す、欄定義に沿った構造化出力のみ許す、従来型 OCR と二重に読んで食い違う欄を目立たせる、ユーザーの必須確認を安全網にする

採否は PoC で決める。装置 2〜3 台分のパネルと紙ノートの写真を 20〜30 枚ずつ集め、従来型 OCR と画像対応 LLM の両方で読み、欄単位の正答率と誤りの種類（桁、小数点、単位、幻覚）を測る。機材の購入は結果を見てから決める。

## 推奨する流れ

1. Web アプリのカメラで撮影し、装置と試料を選択
2. 画像をサーバーへ送信。サーバーはその装置の固有情報の欄に合わせて値を抽出し、欄ごとの候補と確信度を返却
3. アプリ上で欄ごとに確認・訂正。確信度が低い欄を目立たせる
4. 登録。画像は添付として実験データに残る

登録前にユーザーが必ず確認する前提は、brief の Desired Outcome と一致する。

## 写真先行の流れ

装置の前で電波が弱い場面が想定されるなら、「撮影だけ先に済ませ、後で OCR と登録を行う」流れを要件に加える。

- 要望メモの「タブレットは入れ忘れる」への対策になる
- 撮影時点で装置と試料を選んでおけば、後の確認作業が短くなる
- サーバー側 OCR の方が自然に実現できる（端末は画像を保持して送るだけ）

## 設計時に決めること

- OCR エンジンの選定（従来型 OCR と前処理で足りるか、装置ごとに専用認識器を足すか）
- 外部 API の利用可否（組織の情報管理規程と費用の上限）
- 装置ごとの読み取り規則の持ち方（固有情報の欄定義に紐づけるか）
- 確信度の閾値と、確認画面での見せ方
- 写真先行の流れを要件に含めるか
- 画像の保存期間と容量の見積もり

## 未確定事項（現場へ確認）

- 撮影対象は装置のパネルか、紙のノートか、両方か（UC-12 の確認事項）
- パネルの表示形式（7 セグメント、液晶、印字）と、撮影しやすい位置か
- 装置の前での電波状況
- 撮影画像を組織の外へ送ってよいか。外部 API を選択肢に残せるか
